# Content Operations Centre Architecture Pattern

## Problem

English Spelling content needs an operator-managed workflow for editorial changes, audio readiness, monster and reward configuration, approval, publish, and recovery. The legacy account-scoped spelling bundle and import/publish card are not enough because they cannot safely express package-level review, immutable releases, asset provenance, or rollback history.

## Pattern

Use a package-first release model:

1. Operators create a draft package from the current global release.
2. Ordered operations describe the intended content, audio profile, reward, hero exposure, and asset-reference changes.
3. A candidate rebuild materialises the package result and attaches validation, audio, asset, reward, visibility, and conflict scans.
4. Approval records that the final candidate is ready.
5. Publish creates an immutable global release and moves learner runtime to that release.
6. Revert and rollback create explicit recovery history instead of mutating old releases.

## Durable Records

- `content_operation_packages` owns editorial intent and lifecycle state.
- `content_operation_package_operations` owns ordered changes.
- `content_operation_package_candidates` owns derived candidate snapshots and scan envelopes.
- `content_operation_releases` owns immutable published snapshots and release proof.
- `content_operation_audio_jobs` owns TTS job provenance.
- `content_operation_asset_uploads` owns package-scoped monster image upload provenance.
- `content_operation_events` and `content_operation_approvals` own operator audit history.

## Invariants

- Published releases are immutable.
- Learner runtime resolves the current published global spelling release before legacy account content.
- Legacy spelling writes fail closed after global release cutover.
- Audio assets are generated by TTS; admin audio upload is not a supported workflow.
- A pool can have zero, one, or many reward tracks; do not encode a one-pool-one-monster assumption.
- Package edits after approval invalidate approval.
- Override audio generation invalidates approval.
- List endpoints return compact summaries and never inline full snapshots or large proof/scan arrays.

## Security And Capacity Boundaries

- Body caps keep admin payloads bounded.
- `generate-audio` is rate-limited before TTS provider calls.
- `upload-monster-asset` is rate-limited before multipart body reads.
- Admin safe-copy output masks account ids and strips learner or child ids.
- Full release snapshots require a dedicated endpoint; list calls reject inline snapshot expansion.
- Asset previews are private and no-store.

## Recovery Model

Prefer package revert when the operator wants an auditable forward fix. Prefer release rollback when production should return to a known immutable release quickly. Both paths should leave release proof and event history intact.

`spelling.monsterAssetReference` needs manual attention during revert because it represents asset reference metadata rather than a normal structural content row.

## Reuse Guidance

Use this pattern for future subject content only when the subject needs all of:

- operator editorial packages
- approval and publish gates
- immutable learner-visible releases
- scan-derived readiness gates
- asset or generated-media provenance
- auditable recovery

For simple seeded-only content, a generated bundle plus validation script is still cheaper and safer.
